## B. `/runtime-stats` rows that are wrong on JDK 25 (all measured here)

**B1 — `gc.collections.gen2` is not comparable between the two Java cells, or against .NET. Not mentioned anywhere in §4.**
Identical workload (400k × 1 KiB allocations, 60k live, `-Xmx512m`):

| | G1 | ZGC |
|---|---|---|
| natural churn, gen2 bean | `G1 Old Generation` count = **0** | `ZGC Major Cycles` count = **3** |
| after one default `System.gc()` | count = **1** | count = **4** |

G1's old-gen bean increments on **Full GC only** — mixed collections increment `G1 Young Generation`. ZGC's major bean increments on every old-gen cycle. .NET's `dotnet.gc.collections{gen=2}` counts every gen2 including background. So the frozen mapping yields Java-G1 gen2 ≈ 0 while .NET gen2 > 0 on the same work, and the two *Java* cells disagree 3-to-0. §4 decision #1 spends its whole argument on `gen1` and never notices `gen2` is the incomparable row.

**B2 — `gc.pause_total_seconds` is identically `0.0` under ZGC.** Measured: `ZGC Minor Pauses` count=3 **timeMs=0**; `ZGC Major Pauses` count=15 **timeMs=0** (23 pauses / 0 ms after a forced full). `GarbageCollectorMXBean.getCollectionTime()` is millisecond-granular and ZGC pauses are sub-millisecond. G1 on the same workload: 13 ms. The doc's ZGC row ("only the `*Pauses` beans") therefore produces a constant zero in the one cell where GC pause is the interesting variable. No disposition given.

**B3 — Q3 is settled, but the doc's proposed decisive test cannot pass.** With `-XX:+ExplicitGCInvokesConcurrent -Xlog:gc`, 3 × `System.gc()`: `G1 Concurrent GC` **count=6** (the ×2 claim confirmed), **timeMs=0**; `-Xlog:gc` shows Remark 0.315 + 0.190 + 0.221 and Cleanup 0.004 + 0.003 + 0.003 = **0.736 ms**, concurrent-cycle wall time 1.895 + 1.336 + 1.352 = **4.58 ms**. The bean reports STW sub-pause time, not concurrent wall time. But the doc's cited measurement says `timeMs 1`; I get `0`. Both are consistent with STW and neither is reproducible — `assert time ≈ Σ(Remark+Cleanup)` cannot discriminate below 1 ms. Rewrite the acceptance criterion as `count == 2N` plus `time <= ceil(Σ STW)` and drop the `≈`.

**B4 — `config.active_processor_count` read via `HotSpotDiagnosticMXBean` returns `-1`, not `6`, when the flag is not passed.** Measured: `ActiveProcessorCount = -1 {DEFAULT}`. That is exactly the state §3 warns about (a cell whose GC flag silently drops the processor pin), and the doc's read-back would echo `-1` with no assertion catching it. Assert `availableProcessors() == SUT_CORES` — which `phases.py:1065` already does against `build.processor_count` — not the flag.

**B5 — `SoftMaxHeapSize` exists under G1 too, and the §4 decision-3 argument is untested where it matters.** Measured with no flags at all: `SoftMaxHeapSize = 16617832448 {ERGONOMIC}` = `MaxHeapSize`. Under `-XX:+UseZGC -Xmx1g`: `SoftMaxHeapSize = 1073741824 {ERGONOMIC}` = `MaxHeapSize`. So it collapses in *every* cell with a pinned heap, not only the equalized one, and it is not a ZGC-only flag as the section implies. The one case the argument turns on — ZGC with **no** heap flags, where `zArguments.cpp` should give 90% — was never run.

**Rows I confirmed correct (mark these evidenced, not asserted):**
- `com.sun.management.ThreadMXBean.getTotalThreadAllocatedBytes()` **is virtual-thread-aware**: 64 vthreads × 400 × 8 KiB → delta **210,593,192 B**. `isThreadAllocatedMemorySupported/Enabled` both `true` by default.

- `jdk.management.VirtualThreadSchedulerMXBean` exists, module `jdk.management`, `ObjectName jdk.management:type=VirtualThreadScheduler`, methods exactly `getParallelism / setParallelism / getPoolSize / getMountedVirtualThreadCount / getQueuedVirtualThreadCount`.

- `-XX:+ZGenerational` → `OpenJDK 64-Bit Server VM warning: Ignoring option ZGenerational; support was removed in 24.0`; `getVMOption("ZGenerational")` throws `VM option "ZGenerational" does not exist`.
- Origins as claimed: `MaxRAMPercentage=25.0{DEFAULT}`, `UseCompactObjectHeaders=false{DEFAULT}`, `UseTransparentHugePages=false{DEFAULT}`, `EnableDynamicAgentLoading=true{DEFAULT}`, `ThreadStackSize=1024{DEFAULT}`, `GCTimeRatio=12{DEFAULT}`, `ZUncommit=true{DEFAULT}`, `ZUncommitDelay=300{DEFAULT}`.

## E. Fairness asymmetries the document misses

**E1 — A2 is backwards, and it contradicts the repo's own frozen spec. This is the headline defect.**
- `spec/db-access.md:112` freezes the **.NET headline** at `Max Auto Prepare=0` *(Npgsql DEFAULT, off)*, with `=20 / Min Usages=5` as the **"prepared parity" variant**.
- `services/dotnet/Config/LedgerConfig.cs:71` — `MaxAutoPrepare = EnvInt("MAX_AUTO_PREPARE", 0)`.
- `spec/db-access.md:114` — "The asymmetry of the two documented defaults is **the #1 PG fairness lever**."
- `docs/FAIRNESS.md:33` records the round-1 magnitude: enabling it moved the .NET knee **1,468 → 10,426 rps** at the same 20 ms promise, and the round-1 headline was consequently **taken from the parity cell**.

The research doc instead writes A2 as ".NET | Npgsql `Max Auto Prepare=20`, `Min Usages=5` (**explicitly set**; the default is 0/off)", scores the axis "**neither**, by construction", and calls D4 "correct". If Java runs PgJDBC's `prepareThreshold=5` default (server-side prepared from execution 5) against a .NET headline at `Max Auto Prepare=0` (never prepared), the Java:.NET headline ratio is dominated by prepared-vs-unprepared, not by runtime cost. The document proposes no Java analog of the parity cell and lists no Java-side knob for it — and there is no default-vs-default parity available, since matching .NET's headline would require the non-default `prepareThreshold=0` de-tune. Note also that A4 (binary result formats) is *downstream* of this: PgJDBC returns binary results only once a statement is named, so if the parity question is unresolved, A4's steady-state assertion is unresolved with it.

**E2 — JSON date serialization and timezone: no Java-side plan at all, and §3's stated posture actively breaks the frozen contract.**
- `spec/openapi.yaml:201` freezes `created_at` as "RFC3339 UTC, 6 fractional digits, Z"; `spec/schema.sql:29,38` store `timestamptz`; `services/dotnet/Json/Rfc3339Micros.cs` is a **custom converter written specifically to guarantee that**.
- The doc pins `spring.jackson.*` as "untouched (Boot 4 applies **no** feature overrides unless `use-jackson2-defaults=true`)" and specifies **no** serializer, **no** `WRITE_DATES_AS_TIMESTAMPS` disposition, **no** `hibernate.timezone.default_storage`, and **no** `TZ` / `-Duser.timezone` pin. Under exactly that posture a `java.time` field serializes by Jackson's own default rather than Boot 3's overridden one, and `timestamptz` → `Instant`/`OffsetDateTime` normalization is JVM-default-zone dependent. The doc pins `ZoneOffset.UTC` for the **log** formatter only.
- Not a fairness row — an equivalence-suite-blocking row, and the highest-probability P4 implementation failure in the document.

**E3 — warmup-gate sensitivity is asymmetric (follows from B1).** `warmup.py`'s GC-steady gate reads `GcCollections.total()`. With G1 gen2 ≈ 0 and gen1 zero-filled by the doc's own decision, Java's cadence series is effectively `G1 Young Generation` alone, while .NET's is gen0+gen1+gen2. The two SUTs are admitted to measurement on structurally different signals, and round 1's published flagging rate was already 59.5% and language-asymmetric (`docs/FAIRNESS.md:42`). Not listed.

**E4 — HTTP response framing (verify, do not assert).** Spring MVC + Jackson streams into Tomcat's 8 KB output buffer; a response that overflows it goes `Transfer-Encoding: chunked` with no `Content-Length`, while Kestrel's minimal-API JSON path emits `Content-Length` for bodies that complete in the pipe. `GET /customers/{id}/invoices` returns 20 `InvoiceSummary` objects (25% of the mix) and is the endpoint most likely to cross 8 KB. Different framing = different wire bytes, different syscall counts, different vegeta byte accounting. Absent from the 31-row table; check with `curl -sD-` at P4.

**E5 — schema-management posture unpinned.** `spring.jpa.hibernate.ddl-auto` / `hibernate.hbm2ddl.auto` appears nowhere in the document. The schema is shared and owned by `spec/schema.sql`. A `validate` adds `information_schema` round-trips at boot (feeding the in-scope cold-start curve); a `create-drop` against the shared PG would be silent and catastrophic. Must be pinned `none` explicitly and asserted, next to S13.

**E6 — DB-pool fill schedule.** `warmup.py` gates on `db_pool.total >= db_pool.max`. HikariCP at min=max=24 does not open 24 connections synchronously at startup (on-demand plus housekeeper backfill); Npgsql's `Minimum Pool Size` fills on a different schedule. The doc handles the Redis half of that gate (`/readyz` PING, Lettuce `eagerInitialization=false`) and says nothing about the DB half.
