# Hibernate 7 SQL-shape spike — MEASURED, not researched (2026-08-21)

Setup: Spring Boot 4.1.1, Hibernate ORM 7.4.5.Final, PgJDBC 42.7.13, HikariCP 7.0.2,
Temurin 25.0.4, real PostgreSQL **18.4** container with `spec/schema.sql` applied verbatim.
SQL captured with `org.hibernate.resource.jdbc.spi.StatementInspector` wired via
`spring.jpa.properties.hibernate.session_factory.statement_inspector` — this is the
mechanism P4/P5 should use to assert statement shapes in tests.

Entities model the FK as a **scalar `Long customerId` / `Long invoiceId`, not `@ManyToOne`**.
That sidesteps the JPA EAGER-by-default trap entirely, and it is what the frozen SQL wants:
`spec/db-access.sql` selects `customer_id` as a column and never joins.

## Statement-by-statement, against spec/db-access.sql

| id | Hibernate 7.4.5 emits | vs spec | verdict |
|---|---|---|---|
| Q1 | `select i1_0.id,i1_0.created_at,i1_0.currency,i1_0.customer_id,i1_0.status,i1_0.total_minor from invoices i1_0 where i1_0.id=?` | same columns, alphabetised after `id`, aliased | shape-equivalent. **No trailing `LIMIT 1`** — Hibernate is *closer* to spec here than EF Core, which adds one |
| Q2 | `select ii1_0.… from invoice_items ii1_0 where ii1_0.invoice_id=? order by ii1_0.id` | same | shape-equivalent |
| Q3 (derived + `Pageable`) | `… where i1_0.customer_id=? order by i1_0.id desc offset ? rows fetch first ? rows only` | spec says `LIMIT 20 OFFSET $2` | **A THIRD distinct text.** Hibernate uses SQL-standard `OFFSET … FETCH FIRST`; spec/sqlc/ADO use `LIMIT n OFFSET $2`; EF uses `LIMIT $2 OFFSET $3`. All three are plan-identical on PG (same index scan) but differ in `pg_stat_statements` and in prepared-statement signature |
| Q3 (derived + `Limit.of(20)`) | drops `order by` entirely | wrong | unusable — `Limit` without `OrderBy…` in the method name loses the ordering |
| Q3 (native `@Query`) | byte-identical to `spec/db-access.sql` | exact | available if byte parity is wanted |
| Q7/Q3b `existsById` | `select count(*) from customers c1_0 where c1_0.id=?` | spec says `SELECT EXISTS(SELECT 1 …)` | **count, not EXISTS** |
| Q7/Q3b JPQL `count(c) > 0` | `select count(c1_0.id)>0 from customers c1_0 where c1_0.id=?` | still a count | not EXISTS |
| Q7/Q3b native | `SELECT EXISTS(SELECT 1 FROM customers WHERE id = ?)` | exact | the only way to get the spec shape |
| Q4 insert | `insert into invoices (currency,customer_id,status,total_minor) values (?,?,?,?) returning id,created_at` | spec `RETURNING id, created_at` | **exact semantics.** Hibernate 7 uses `RETURNING` on PG for IDENTITY, and `@Generated(event = INSERT)` on `created_at` brings the DB default back with **no second SELECT** |
| Q5 item insert | **[CORRECTED]** on the wire it is `insert into invoice_items (…) values ($1,…,$6)` **+ a literal newline + `RETURNING *`**, appended client-side by PgJDBC's `getGeneratedKeys` path. `StatementInspector` never sees the appended clause, so the first draft of this file wrongly recorded "no returning". **All seven item columns come back for every row**, not just `id`. | spec: N inserts in ONE batched round trip | **see the batching finding below**; the `RETURNING *` makes it worse than the round-trip count alone suggests |
| Q6 native | `UPDATE customers SET balance_minor = balance_minor + ? WHERE id = ?` | exact | atomic increment, byte-identical |
| Q6 JPQL bulk | `update customers c1_0 set balance_minor=(c1_0.balance_minor+?) where c1_0.id=?` | atomic, aliased, extra parens | semantically correct, text differs |

## FINDING 1 (material, measured): IDENTITY disables insert batching

Controlled experiment, same session, same `hibernate.jdbc.batch_size=8`:

| entity | rows | `StatementInspector.inspect()` calls |
|---|---|---|
| `Customer` — **assigned** `@Id` | 6 | **1** (one PreparedStatement, `addBatch()` x6) |
| `InvoiceItem` — `@GeneratedValue(IDENTITY)` | 6 | **6** (six separate prepares) |

Hibernate logs `HHH100501: Automatic JDBC statement batching enabled (maximum batch size 8)`
and then does not use it for the IDENTITY entity. `spec/schema.sql` pins
`invoice_items.id GENERATED ALWAYS AS IDENTITY`, so this is not avoidable inside JPA.

**Consequence for the benchmark.** `spec/db-access.md` currently pins the create path as
`existence(1) + BEGIN + header insert RETURNING(1) + ONE batched round-trip [Q5 xN + Q6] + COMMIT`
and says round-trip counts are "ASSERTED EQUAL at integration". **That assertion cannot hold
for Hibernate.** With 3–8 items per invoice and `create_invoice` at 15% of the mix, Java pays
3–8 round trips where EF Core pays 1. It costs Java, it is real production Hibernate behaviour,
and it must be disclosed rather than engineered around.

Options, and the recommendation:
- **(A) Accept and disclose** — keep pure Spring Data JPA, rewrite the round-trip ledger in
  `spec/db-access.md` to the real per-stack counts, add the row to `docs/FAIRNESS.md`.
  **Recommended.** The headline is ORM vs ORM; this *is* what the ORM costs.
- (B) Drop to `JdbcTemplate.batchUpdate` for the item inserts — production-common, but it
  makes the Java side "JPA + hand-JDBC" and recreates exactly the round-1 asymmetry that
  `docs/FAIRNESS.md` had to disclose for Go ("the two hottest paths are EF Core against
  hand-written pgx"). Rejected unless measurement shows it dominates the headline.
- (C) Change the schema to a sequence — forbidden, `spec/schema.sql` is frozen and IDENTITY
  is a deliberate pin.

## FINDING 2: `PageRequest` + `OrderBy…` in the method name duplicates the sort

`findByCustomerIdOrderByIdDesc(1L, PageRequest.of(2, 20, Sort.by(DESC,"id")))` emits
`order by i1_0.id desc,i1_0.id desc`. Use the method-name ordering **or** the `Sort`, never
both. Harmless to the plan, ugly in `pg_stat_statements`, and a trap worth a test.

## FINDING 3 **[CORRECTED]**: `@Transactional(readOnly = true)` DOES change the wire

The first draft of this file claimed it did not. That was a false negative from
`StatementInspector`, which cannot see transaction control. PostgreSQL's own log:

```
LOG:  statement: BEGIN READ ONLY                       <- readOnly = true
LOG:  execute <unnamed>: select i1_0.id,… from invoices i1_0 where i1_0.id=$1
LOG:  execute S_1: ROLLBACK                            <- not COMMIT
...
LOG:  statement: BEGIN                                 <- the write path, for contrast
```

Mechanism: Spring's `HibernateJpaVendorAdapter` holds the connection for the transaction,
so `HibernateJpaDialect` calls `Connection.setReadOnly(true)`, and PgJDBC's default
`readOnlyMode=transaction` turns that into `BEGIN READ ONLY`. A read-only transaction is
also ended with `ROLLBACK`, not `COMMIT`.

**Parity impact.** The .NET read path must be compared against this at the wire, not
assumed equal. If EF Core opens no explicit transaction for a single read, Java pays two
extra round trips per cache-miss read (`BEGIN READ ONLY` + `ROLLBACK`) that .NET does not —
on 30% of the mix. Quantify at P5 and either equalise or disclose with the side it costs
named. This is precisely the class of asymmetry round 1 shipped four of.

## FINDING 4: `prepareThreshold=5` observed switching over, mid-transaction

The server log shows the switch happening exactly where the default says it should — the
first four executions of the item insert are unnamed, the fifth becomes a named
server-side prepared statement:

```
execute <unnamed>: insert into invoice_items (…) values ($1,…,$6) RETURNING *   x4
execute S_1:       insert into invoice_items (…) values ($1,…,$6) RETURNING *   <- 5th
```

So PgJDBC's `prepareThreshold=5` is doing exactly what `spec/db-access.md` will claim, and
`pg_stat_statements` sees `$n` parameterised text. Directly comparable to Npgsql at
`Max Auto Prepare=20` / `Auto Prepare Min Usages=5` (decision D4) — and note the two
thresholds now match, which is the point of D4.

## FINDING 5: per-connection setup chatter (one-time, both stacks pay their own)
Each new PgJDBC connection emits `SET application_name`, `SHOW TRANSACTION ISOLATION LEVEL`,
`select version()`, `select current_schema()`, `select current_catalog`, a
`pg_settings` lookup and a large `pg_get_keywords()` query. All one-time per physical
connection, and with `DB_POOL_MIN == DB_POOL_MAX` the pool is opened during warmup, so none
of it lands in a measured window. Worth recording in the P5 wire ledger anyway, because
Npgsql's equivalent (and its `DISCARD ALL` on pooled checkout, which is **per checkout**,
not per connection) is a different shape.

## Cache-miss read path (Q1+Q2)
Hibernate issues them as **two sequential statements**, same as EF Core. So on this path
Java and .NET are symmetric, and only the round-1 Go/pgx batch was the odd one out. Good:
one fewer asymmetry than round 1 carried.

# JVM `/runtime-stats` mapping — MEASURED on Temurin 25.0.4 (2026-08-21)

Everything below was read off a running JVM, not from documentation. These strings go
verbatim into the `spec/runtime-stats.md` rewrite, so they had to be observed.

## GarbageCollectorMXBean names — they differ per collector and ZGC splits cycles from pauses

**G1** (`-XX:+UseG1GC`), 3 beans:

| bean name | pools |
|---|---|
| `G1 Young Generation` | G1 Eden Space, G1 Survivor Space, G1 Old Gen |
| `G1 Concurrent GC` | G1 Old Gen |
| `G1 Old Generation` | G1 Eden Space, G1 Survivor Space, G1 Old Gen |

**Generational ZGC** (`-XX:+UseZGC`), 4 beans:

| bean name | pools |
|---|---|
| `ZGC Minor Cycles` | ZGC Young Generation, ZGC Old Generation |
| `ZGC Minor Pauses` | ZGC Young Generation, ZGC Old Generation |
| `ZGC Major Cycles` | ZGC Young Generation, ZGC Old Generation |
| `ZGC Major Pauses` | ZGC Young Generation, ZGC Old Generation |

**TRAP:** under ZGC, *Cycles* and *Pauses* are SEPARATE beans over the same pools. Summing
`getCollectionCount()` across all four double-counts collections, and summing
`getCollectionTime()` across all four adds concurrent-cycle wall time to stop-the-world
pause time. `gc.collections` must read only `*Cycles`; `gc.pause_total_seconds` must read
only `*Pauses`. Under G1 every bean is a real collection and pause time is the STW time.

`-XX:+ZGenerational` is **removed**: the JVM prints
`Ignoring option ZGenerational; support was removed in 24.0`. `-XX:+UseZGC` alone is
generational on 25.

## MemoryPoolMXBean names
- G1: `G1 Eden Space`, `G1 Survivor Space`, `G1 Old Gen`
- ZGC: `ZGC Young Generation`, `ZGC Old Generation`
- Non-heap (both): `Metaspace`, `Compressed Class Space`, `CodeHeap 'non-nmethods'`,
  `CodeHeap 'profiled nmethods'`, `CodeHeap 'non-profiled nmethods'`

Use `MemoryMXBean.getHeapMemoryUsage()` for `heap_in_use_bytes` / `heap_committed_bytes` —
one call, no per-pool iteration, correct under both collectors.

# Wire timestamp format (P4 trap #2) — measured

Frozen contract: RFC3339 UTC, exactly 6 fractional digits, `Z` (`spec/logging.md`,
`spec/openapi.yaml`). .NET holds it with `"yyyy-MM-dd'T'HH:mm:ss.ffffff'Z'"`
(`services/dotnet/Json/Rfc3339Micros.cs`).

Java equivalent, verified:
`DateTimeFormatter.ofPattern("uuuu-MM-dd'T'HH:mm:ss.SSSSSS'Z'").withZone(ZoneOffset.UTC)`

| input `Instant` | `Instant.toString()` — WRONG | formatter — REQUIRED | len |
|---|---|---|---|
| `2026-06-06T00:00:00Z` | `2026-06-06T00:00:00Z` | `2026-06-06T00:00:00.000000Z` | 27 |
| `…00.100Z` | `…00.100Z` | `…00.100000Z` | 27 |
| `…00.123456Z` | `…00.123456Z` | `…00.123456Z` | 27 |
| `…00.123456789Z` | `…00.123456789Z` | `…00.123456Z` | 27 |
| `…40.999999999Z` | `…40.999999999Z` | `…40.999999Z` | 27 |

Confirms the trap: both `Instant.toString()` and `OffsetDateTime.toString()` emit
**variable** precision and would fail the golden vectors on the first all-zero fraction.
The formatter **truncates** (`.999999999` -> `.999999`), it does not round — same direction
as .NET's `ffffff`. PostgreSQL `timestamptz` is microsecond-precision, so truncation is
lossless for every DB-sourced value; only in-process `now()` has nanos to lose.

# GC bean comparability — two rows of `/runtime-stats` cannot be mapped honestly

Measured 2026-08-21 on Temurin 25.0.4, identical workload (400k x 1 KiB allocations,
60k retained, `-Xmx512m`), G1 against generational ZGC.

| | G1 | generational ZGC |
|---|---|---|
| natural churn, "gen0" bean | `G1 Young Generation` count=2, timeMs=7 | `ZGC Minor Cycles` count=1, timeMs=9 |
| natural churn, "gen2" bean | `G1 Old Generation` **count=0**, timeMs=0 | `ZGC Major Cycles` **count=3**, timeMs=20 |
| after one `System.gc()`, "gen2" | count=**1**, timeMs=5 | count=**4**, timeMs=30 |
| pause beans | G1 has none separately: the cycle beans ARE the STW time | `ZGC Minor Pauses` count=3 **timeMs=0**; `ZGC Major Pauses` count=15 **timeMs=0** |

## FINDING 6: `gc.collections.gen2` is NOT comparable across collectors

G1's `G1 Old Generation` bean increments on **Full GC only** — G1's mixed collections,
which are how it actually reclaims old regions, increment `G1 Young Generation`. ZGC's
`ZGC Major Cycles` increments on **every** old-generation cycle. On identical work that is
**0 versus 3**.

So a frozen mapping of `gen2 -> the old-generation bean` yields:
- Java/G1 gen2 approximately 0 under any normal workload,
- Java/ZGC gen2 counting real work,
- .NET gen2 (`dotnet.gc.collections{gen=2}`) counting every gen2 including background.

Three different meanings under one field name. The `heap-default` and `heap-equalized`
cells would disagree three-to-zero on the same load, and neither is comparable to .NET.

**Disposition for `spec/runtime-stats.md` (W27):** report `gc.collections` per collector
under the **bean's own name** and set the `gen0/gen1/gen2` triple to `null` for Java rather
than forcing a false triple. The frozen SHAPE stays identical (the contract already allows
a present-but-null field where a runtime has no analog); the lie does not get frozen.
Whatever is chosen must be chosen before P7, and it must not be a rename.

**Consequence for the warmup gate, and it is language-asymmetric:** `warmup.py`'s
`gc_steady` cadence series is built from `GcCollections.total()`. If Java's triple is
null-filled, Java's cadence signal is effectively `G1 Young Generation` alone while .NET's
is gen0+gen1+gen2 — the two SUTs would be admitted to measurement on structurally
different signals. Round 1's flagging was already 59.5% and language-asymmetric; this is a
mechanism by which round 2 could repeat it. Fix the cadence source as part of the B2
recalibration (W21), not by pretending the triple maps.

## FINDING 7: `gc.pause_total_seconds` is identically 0.0 under ZGC

`GarbageCollectorMXBean.getCollectionTime()` returns **milliseconds**, and ZGC's pauses are
sub-millisecond by design. Measured: 3 minor pauses -> 0 ms, 15 major pauses -> 0 ms,
23 pauses after a forced full GC -> still **0 ms**. G1 on the same workload reports 7 ms
and 5 ms.

The field would therefore be a constant zero in exactly the cell where GC pause is the
interesting variable, and a reader comparing "Java pause total" against .NET would read
ZGC as pauseless rather than as sub-millisecond.

**Disposition:** report ZGC pause **counts** (which are real: 3 and 15) and set
`pause_total_seconds` to `null` under ZGC with the reason recorded, or source pause time
from `-Xlog:gc` outside the measured window. Do **not** publish 0.0.

ZGC pauses are also not 1:1 with cycles — one minor cycle carried three minor pauses
(mark start / mark end / relocate start). Any "pauses per collection" derivation must
account for that.

## FINDING 8: `ActiveProcessorCount` reads back as `-1`, not the effective count

`HotSpotDiagnosticMXBean.getVMOption("ActiveProcessorCount")` returns `-1 {DEFAULT}` when
the flag is not passed, even though `Runtime.availableProcessors()` correctly returns the
cpuset size (measured: 6 under `--cpuset-cpus=0-5`). So the flag read-back is **not** the
assertion to make: assert `availableProcessors() == SUT_CORES`, which `phases.py` already
does against `/runtime-stats` `build.processor_count`, and record the flag's origin only
as disclosure.
